# Phase 2 — Math Engine: Complete Specification

Everything Chapter 4 + Chapter 7.1–7.3 require, wired into M0/M1/M4/M6/M9. This is the phase that turns UDDP's approximate bounds tests into exact integer solvers.

---

## 2.0 What Phase 2 is

**Input:** M0–M13 with approximate bounds tests, a working Fourier-Motzkin over reals, and a gcd filter.

**Output:** exact integer decision procedures for systems of linear Diophantine equations and inequalities, wired into every level that needs them. Plus the certificate vocabulary to carry the results.

**The one-line goal:** replace "the real relaxation has a solution, therefore *maybe* there's an integer solution" with "here is the exact integer solution, or a proof none exists."

**What Phase 2 does NOT do:**
- No FUD chains (Phase 3)
- No IV detection (Phase 4)
- No storage association, no points-to, no interprocedural (Phases 5–8)
- No frontend (Phase 9)

**What Phase 2 unlocks for later phases:**
- Phase 3's FUD chains need `gcd` and `findgcd` for the IV algebra
- Phase 4's IV detection needs `findgcd` for step computations
- Phase 5's runtime testing needs `dark_shadow` to verify guards
- Phase 8's interprocedural constant propagation needs the integer equation solver
- SPP Layer 2's non-unimodular transformations need HNF

## 2.2 `solver/gcd.rs` — Extended Euclidean and gcd test

**Wolfe §4.2.1.** The most-used primitive in the entire codebase. Every level calls it.

### The formulas

**Euclid's algorithm:**
```
gcd(a, b):
    if b = 0: return a
    return gcd(b, a mod b)

a mod b = a - b·⌊a/b⌋
```

**Extended Euclid (findgcd):**
```
procedure findgcd(a, b) returns (g, x, y):
    g₀ = a ; g₁ = b
    x₀ = 1 ; x₁ = 0
    y₀ = 0 ; y₁ = 1
    repeat:
        d = g₀ div g₁
        g₂ = g₁ - d·g₀
        g₀ = g₁ ; g₁ = g₂
        x₂ = x₁ - d·x₀
        x₀ = x₁ ; x₁ = x₂
    until g₂ = 0
    g = g₀
    x = x₁
    y = (g - a·x) / b
    if g < 0:
        g = -g ; x = -x ; y = -y
    return (g, x, y)
```

### The API

```rust
/// gcd(a, b) — Euclid's algorithm.
pub fn gcd(a: i64, b: i64) -> i64;

/// Extended gcd: returns (g, x, y) with a·x + b·y = g.
pub fn findgcd(a: i64, b: i64) -> (i64, i64, i64);

/// gcd over a slice. gcd of empty slice is 0.

/// Single-equation gcd test.
/// Returns true iff gcd(a, b) divides c.
pub fn gcd_test_2(a: i64, b: i64, c: i64) -> bool;

/// Multi-variable gcd test.
/// Returns true iff gcd(a₁, ..., aₙ) divides c.
pub fn gcd_test_many(coeffs: &[i64], c: i64) -> bool;

/// General solution to a·x + b·y = c.
/// Returns Some((x₀, y₀, dx, dy)) where (x₀ + dx·t, y₀ + dy·t) for t ∈ Z
/// is the full solution set, or None if gcd(a,b) ∤ c.
pub fn general_solution_2(a: i64, b: i64, c: i64) -> Option<(i64, i64, i64, i64)>;
```

### The formulas in code

```rust
pub fn gcd(mut a: i64, mut b: i64) -> i64 {
    a = a.abs();
    b = b.abs();
    while b != 0 {
        let t = b;
        b = a % b;
        a = t;
    }
    a
}

pub fn findgcd(a: i64, b: i64) -> (i64, i64, i64) {
    let mut g0 = a;
    let mut g1 = b;
    let mut x0 = 1i64;
    let mut x1 = 0i64;
    let mut y0 = 0i64;
    let mut y1 = 1i64;
    loop {
        if g1 == 0 { break; }
        let d = g0 / g1;
        let g2 = g0 - d * g1;
        g0 = g1; g1 = g2;
        let x2 = x0 - d * x1;
        x0 = x1; x1 = x2;
        let y2 = y0 - d * y1;
        y0 = y1; y1 = y2;
    }
    let mut g = g0;
    let mut x = x0;
    let mut y = if b != 0 { (g0 - a * x0) / b } else { y0 };
    if g < 0 { g = -g; x = -x; y = -y; }
    (g, x, y)
}
```

### General solution

For `a·x + b·y = c`:
- If `g = gcd(a, b)` does not divide `c`, no solution
- Otherwise: `x = (c/g)·x₀ + (b/g)·t`, `y = (c/g)·y₀ - (a/g)·t`

```rust
pub fn general_solution_2(a: i64, b: i64, c: i64) -> Option<(i64, i64, i64, i64)> {
    let (g, x0, y0) = findgcd(a, b);
    if g == 0 {
        return if c == 0 { Some((0, 0, 0, 0)) } else { None };
    }
    if c % g != 0 { return None; }
    let mult = c / g;
    Some((mult * x0, mult * y0, b / g, -a / g))
}
```

### Tests

- `gcd` identity: `gcd(a, b) == gcd(b, a)`, `gcd(a, 0) == a`, `gcd(0, 0) == 0`
- `findgcd` correctness: `a·x + b·y == g` for random `(a, b)`
- Sign handling: negative `a`/`b` produce positive `g`
- `general_solution_2`: for random `(a, b, c)` where `gcd(a,b) | c`, verify that `(x₀ + dx·t, y₀ + dy·t)` satisfies the equation for `t ∈ {-10, ..., 10}`

**Lines:** ~150 + ~100 tests.

## 2.3 `solver/inverse.rs` — Matrix inverse

**Wolfe §4.1.6.** Solves square nonsingular systems.

### The algorithm

```
procedure Invert(A) returns (B, r):
    initialize B to I
    r = 0
    for j = 1 to n:
        find k ∈ [r+1:n] such that a_kj ≠ 0
        if no such k:
            A is singular at this column (rank < n)
        else:
            r = r + 1
            if k ≠ r:
                interchange row A_[r] with row A_[k]
                interchange row B_[r] with row B_[k]
            if a_rj ≠ 1:
                c = a_rj
                divide row A_[r] by c
                divide row B_[r] by c
            for i = 1 to n:
                if i ≠ r and a_ij ≠ 0:
                    α = a_ij
                    A_[i] = A_[i] - α·A_[r]
                    B_[i] = B_[i] - α·B_[r]
    return (B, r)
```

### The API

```rust
pub struct Matrix {
    pub rows: usize,
    pub cols: usize,
    pub data: Vec<i64>,   // row-major
}

impl Matrix {
    pub fn new(rows: usize, cols: usize) -> Self;
    pub fn get(&self, i: usize, j: usize) -> i64;
    pub fn set(&mut self, i: usize, j: usize, v: i64);
    pub fn identity(n: usize) -> Self;
    pub fn transpose(&self) -> Self;
    pub fn matmul(&self, other: &Matrix) -> Option<Matrix>;
}

/// Compute A⁻¹ or the rank. Returns (B, r) where:
///   - if r == n: A is nonsingular, B = A⁻¹
///   - if r < n:  A has rank r, B is undefined
pub fn invert(a: &Matrix) -> (Option<Matrix>, usize);

/// Compute det(A) for square A. Returns None if singular.
pub fn determinant(a: &Matrix) -> Option<i64>;

/// Compute rank of A (any shape).
pub fn rank(a: &Matrix) -> usize;

/// Unimodularity test: det(A) == ±1.
pub fn is_unimodular(a: &Matrix) -> bool;
```

### The formulas in code

```rust
pub fn invert(a: &Matrix) -> (Option<Matrix>, usize) {
    let n = a.rows;
    assert_eq!(a.rows, a.cols);
    let mut work = a.clone();
    let mut b = Matrix::identity(n);
    let mut r = 0usize;

    for j in 0..n {
        // find pivot
        let mut pivot = None;
        for k in r..n {
            if work.get(k, j) != 0 { pivot = Some(k); break; }
        }
        let k = match pivot { Some(k) => k, None => continue };

        if k != r {
            work.swap_rows(r, k);
            b.swap_rows(r, k);
        }
        let pv = work.get(r, j);
        if pv != 1 {
            work.scale_row(r, pv);   // requires exact division
            b.scale_row(r, pv);
        }
        for i in 0..n {
            if i == r { continue; }
            let alpha = work.get(i, j);
            if alpha != 0 {
                work.sub_row(i, r, alpha);
                b.sub_row(i, r, alpha);
            }
        }
        r += 1;
    }

    if r == n { (Some(b), n) } else { (None, r) }
}
```

**Note:** exact integer division only works if the pivot divides cleanly. For general integer matrices, `invert` computes the **rational inverse**. To stay in integers, the algorithm must use fraction-free Gaussian elimination (Bareiss) — or accept that `invert` returns `Option<Matrix>` only for matrices whose inverse is integral.

**Decision:** keep `invert` for integer-valued inverses; add `invert_rational` returning `Vec<(i64, i64)>` (numerator, denominator) for the general case. UDDP mostly needs unimodular inverses (where the inverse is always integral).

### Tests

- `A · A⁻¹ == I` for random unimodular `A`
- `det(A · B) == det(A) · det(B)` for random integer matrices
- `rank(A) + nullity(A) == n`
- `is_unimodular` matches `|det(A)| == 1`

**Lines:** ~200 + ~150 tests.

## 2.4 `solver/hnf.rs` — Hermite Normal Form

**Wolfe §4.2.3.** The most important single algorithm in Phase 2.

### The definition

For integer matrix `A` (n×m, rank n):
```
There exists m×m unimodular U such that A·U = H
where H is in Hermite Normal Form:
    - H is lower trapezoidal
    - h_ii > 0 for all i
    - h_ii ≥ h_ij for all j > i
    - H is unique
```

### Algorithm Hermite

```
procedure Hermite(A) returns (H, U):
    initialize H to A
    initialize U to I
    for i = 1 to n:
        Reduce(i, i+1:n, H, U)
        if h_ii < 0:
            negate h_[i]
            negate u_[i]
        for j = 1 to i-1:
            α = |h_ij / h_ii|
            h_[j] = h_[j] - α·h_[i]
    return (H, U)
end Hermite

procedure Reduce(row i, columns j:n, H, U):
    for k = j to n:
        if h_ik ≠ 0:
            a = h_ii ; b = h_ik
            findgcd(a, b, g, x, y)
            p = x·h_[i] + y·h_[k]
            q = -(b/g)·h_[i] + (a/g)·h_[k]
            h_[i] = p ; h_[k] = q
            v = x·u_[i] - (b/g)·u_[k]
            w = y·u_[i] + (a/g)·u_[k]
            u_[i] = v ; u_[k] = w
end Reduce
```

### The API

```rust
/// Compute the HNF of A together with the unimodular transform U.
/// Returns (H, U) with A·U = H.
pub fn hermite(a: &Matrix) -> (Matrix, Matrix);

/// Reduce a single row to a single nonzero (used by ReduceMatrix).
/// Reduces M[j] and M[k] jointly so that M[k] becomes zero in row i.

/// Reduce matrix to column echelon form (used by the general integer solver).
/// Returns (D, U) with A·U = D.
pub fn reduce_matrix(a: &Matrix) -> (Matrix, Matrix);
```

### The formulas in code

```rust
pub fn hermite(a: &Matrix) -> (Matrix, Matrix) {
    let n = a.rows;
    let m = a.cols;
    let mut h = a.clone();
    let mut u = Matrix::identity(m);

    for i in 0..n {
        // Reduce h[i, i+1..m] to zero
        for k in (i + 1)..m {
            if h.get(i, k) == 0 { continue; }
            let a_ii = h.get(i, i);
            let b_ik = h.get(i, k);
            let (g, x, y) = findgcd(a_ii, b_ik);
            // new h[i] = x·h[i] + y·h[k]
            // new h[k] = -(b/g)·h[i] + (a/g)·h[k]
            let p_row = h.combine_rows(i, k, x, y);
            let q_row = h.combine_rows(i, k, -b_ik / g, a_ii / g);
            h.set_row(i, p_row);
            h.set_row(k, q_row);
            // same operations on U
            let p_u = u.combine_rows(i, k, x, y);
            let q_u = u.combine_rows(i, k, -b_ik / g, a_ii / g);
            u.set_row(i, p_u);
            u.set_row(k, q_u);
        }
        // Ensure h_ii > 0
        if h.get(i, i) < 0 {
            h.negate_row(i);
            u.negate_row(i);
        }
        // Reduce h[i, 0..i] to canonical range
        for j in 0..i {
            let h_ij = h.get(i, j);
            let h_ii = h.get(i, i);
            let alpha = h_ij / h_ii;
            h.sub_row(j, i, alpha);
            u.sub_row(j, i, alpha);
        }
    }

    (h, u)
}
```

### What HNF unlocks

1. **Solving `A·x = b` in integers.** Reduce `A·U = H`, then `H·t = b` where `x = U·t`. `H` is trapezoidal, so back-substitution gives `t` if any solution exists.
2. **Lattice basis.** Nonzero columns of `H` form a basis of `L(A) = {A·x : x ∈ Z^m}`.
3. **Non-unimodular loop transformations.** For `T = H·U`, apply `U` first (unimodular, preserves integer points) then `H` (introduces strides `h_mm`). Used in SPP Layer 2 for tiling with non-unit strides.
4. **Column echelon form** for the general integer solver.

### Tests

- `A·U == H` for random integer matrices `A`
- `det(U) == ±1` (unimodularity) for every `U` produced
- `H` is lower trapezoidal
- `h_ii > 0` for all `i`
- `h_ii >= h_ij` for `j > i`
- Idempotence: `hermite(H)` returns `H` unchanged when `H` is already in HNF

**Lines:** ~400 + ~250 tests.

## 2.5 `solver/dark_shadow.rs` — Integer Fourier-Motzkin

**Wolfe §4.6.** The piece that makes M4 exact.

### The formulas

**Real projection (existing FM):**
For two bounds `α·x ≤ c_u` and `c_l ≤ β·x` (where `β < 0`):
```
α·c_l ≤ β·c_u
```

**Dark shadow condition:**
```
β·c_u - α·c_l ≥ α·β - α - β + 1
```

If the dark shadow holds, there exists an integer multiple of `α·β` between the bounds. This guarantees an integer solution when the real projection alone would be inconclusive.

### Algorithm IntegerInequality

```
procedure ProjectInt(A, b):
    inexact = False
    repeat:
        choose variable x_j
        L = {i | a_ij < 0}
        U = {i | a_ij > 0}
        if L or U is empty: unconstrained
        for i in L ∪ U:
            g = |gcd(a_i1, a_i2, ...)|
            divide row A_[i] by g
            b_i = floor(b_i / g)
        for i in L:
            for k in U:
                add a_kj·A_[i] - a_ij·A_[k] ≤ a_kj·b_i - a_ij·b_k
                if |a_kj·a_ij| > 1: inexact = True
        ignore L, U
    until done
end ProjectInt
```

### The dark shadow variant

```
procedure ProjectInt_Dark(A, b):
    inexact = False
    darkempty = False
    repeat:
        choose variable x_j
        compute real projection
        if inexact and not darkempty:
            compute dark shadow with:
                a_kj·A_[i] - a_ij·A_[k] ≤ a_kj·b_i - a_ij·b_k
                    + a_kj·a_ij + a_kj - a_ij - 1
            if dark shadow is empty: darkempty = True
    until done
end ProjectInt_Dark
```

### The API

```rust
pub struct IntSystem {
    pub constraints: Vec<IntConstraint>,
}

pub struct IntConstraint {
    pub coeffs: Vec<i64>,
    pub constant: i64,   // coeffs·x ≤ constant
}

pub enum IntSolution {
    /// Exact integer solution exists.
    Sat(Vec<i64>),
    /// No integer solution.
    Unsat,
    /// Real solution may exist, but integer solution undetermined.
    Unknown,
}

/// Fourier-Motzkin with integer tightening.
pub fn project_int(sys: &IntSystem, eliminate: usize) -> IntSystem;

/// Full solver: does an integer solution exist?
pub fn solve_int(sys: &IntSystem) -> IntSolution;

/// Dark shadow test for a single pair of bounds.
pub fn dark_shadow_holds(
    alpha: i64, c_u: i64,
    beta: i64, c_l: i64,
) -> bool {
    beta * c_u - alpha * c_l >= alpha * beta - alpha - beta + 1
}
```

### The formulas in code

```rust
pub fn dark_shadow_holds(alpha: i64, c_u: i64, beta: i64, c_l: i64) -> bool {
    let lhs = beta.saturating_mul(c_u).saturating_sub(alpha.saturating_mul(c_l));
    let rhs = alpha.saturating_mul(beta)
        .saturating_sub(alpha)
        .saturating_sub(beta)
        .saturating_add(1);
    lhs >= rhs
}

pub fn project_int(sys: &IntSystem, j: usize) -> IntSystem {
    // Partition constraints by sign of coeffs[j]
    let mut lower = Vec::new();  // coeffs[j] < 0 → x_j ≥ ...
    let mut upper = Vec::new();  // coeffs[j] > 0 → x_j ≤ ...
    let mut other = Vec::new();  // coeffs[j] == 0

    for c in &sys.constraints {
        match c.coeffs[j].cmp(&0) {
            Ordering::Less => lower.push(c.clone()),
            Ordering::Greater => upper.push(c.clone()),
            Ordering::Equal => other.push(c.clone()),
        }
    }

    // Integer tightening: divide each row by gcd of its coefficients
    let tighten = |c: &IntConstraint| -> IntConstraint {
        let g = gcd_many(&c.coeffs).abs();
        if g <= 1 { return c.clone(); }
        IntConstraint {
            coeffs: c.coeffs.iter().map(|&x| x / g).collect(),
            constant: c.constant.div_euclid(g),
        }
    };
    let lower: Vec<_> = lower.iter().map(tighten).collect();
    let upper: Vec<_> = upper.iter().map(tighten).collect();

    // Cross-multiply: for each (l, u) pair, add new constraint
    let mut out = other;
    for l in &lower {
        for u in &upper {
            let a_lj = l.coeffs[j];  // negative
            let a_uj = u.coeffs[j];  // positive
            let mut new_coeffs = vec![0i64; l.coeffs.len()];
            for k in 0..l.coeffs.len() {
                new_coeffs[k] = a_uj * l.coeffs[k] - a_lj * u.coeffs[k];
            }
            let new_const = a_uj * l.constant - a_lj * u.constant;
            out.push(IntConstraint { coeffs: new_coeffs, constant: new_const });
        }
    }
    IntSystem { constraints: out }
}
```

### The dark shadow arm (added to `project_int` when `inexact`)

When `|a_kj · a_ij| > 1`, the projection is inexact: the real relaxation has a solution that may not be integral. Add the dark shadow constraint alongside the real one:

```rust
if (a_uj * a_lj).abs() > 1 {
    let dark_const = new_const + a_uj * a_lj + a_uj - a_lj - 1;
    out.push(IntConstraint { coeffs: new_coeffs.clone(), constant: dark_const });
    inexact = true;
}
```

If the dark shadow system is empty but the real system is not, the real solution may be non-integral.

### Tests

- For random `IntSystem`, `solve_int` agrees with brute-force enumeration over a bounded box
- Dark shadow: for random `(α, c_u, β, c_l)`, verify the dark shadow implies an integer solution by enumeration
- Tightening: `(a/g)·x ≤ floor(c/g)` is equivalent to `a·x ≤ c` for integer `x`
- FM over integers with `inexact` flag: verify the flag is set iff `|a_kj · a_ij| > 1` for some pair

**Lines:** ~300 + ~250 tests.

## 2.6 `solver/extreme.rs` — Full Extreme for nonrectangular regions

**Wolfe §4.7.** The piece that makes M0–M2 exact on triangular/trapezoidal loops.

### The formulas

**Single-variable bounds (existing):**
```
min f = a⁺·l + a⁻·u
max f = a⁺·u + a⁻·l
where a⁺ = max(a, 0), a⁻ = max(-a, 0)
```

**The μ and ν functions:**
```
μ(a, b, p, q, ε) = (a + b)·p + b·ε - (q - p - ε)·(a⁻ - b)⁺
ν(a, b, p, q, ε) = (a + b)·p + b·ε + (q - p - ε)·(a⁺ + b)⁺
```

**Bounds test at level ℓ:**
```
μ̄ = Σ_{r=1}^{ℓ-1} μ(a_r - b_r, 0, p_r, q_r, 0)
   + μ(a_ℓ, -b_ℓ, p_ℓ, q_ℓ, 1)
   + Σ_{r=ℓ+1}^{m} [μ(a_r, 0, p_r, q_r, 0) + μ(-b_r, 0, p_r, q_r, 0)]

ν̄ = Σ_{r=1}^{ℓ-1} ν(a_r - b_r, 0, p_r, q_r, 0)
   + ν(a_ℓ, -b_ℓ, p_ℓ, q_ℓ, 1)
   + Σ_{r=ℓ+1}^{m} [ν(a_r, 0, p_r, q_r, 0) + ν(-b_r, 0, p_r, q_r, 0)]

Test: μ̄ ≤ b₀ - a₀ ≤ ν̄
```

**Nonrectangular Extreme:**
```
For function f(x) = F·x + f₀ and region:
    l_{i0} + Σ_{j<i} l_{ij}·x_j ≤ x_i ≤ u_{i0} + Σ_{j<i} u_{ij}·x_j

Bounding functions:
    b_m(x) = a_m(x) = f(x)
    b_{n-1,j} = b_{n,j} + b_{nn}⁺·l_{nj} + b_{nn}⁻·u_{nj}
    a_{n-1,j} = a_{n,j} + a_{nn}⁺·u_{n,j} + a_{nn}⁻·l_{n,j}
```

### The formulas in code

```rust
fn pos(x: i64) -> i64 { if x > 0 { x } else { 0 } }
fn neg(x: i64) -> i64 { if x < 0 { -x } else { 0 } }

pub fn mu(a: i64, b: i64, p: i64, q: i64, eps: i64) -> i64 {
    let s = a + b;
    let first = s * p + b * eps;
    let second = (q - p - eps) * pos(neg(a) - b);
    first - second
}

pub fn nu(a: i64, b: i64, p: i64, q: i64, eps: i64) -> i64 {
    let s = a + b;
    let first = s * p + b * eps;
    let second = (q - p - eps) * pos(pos(a) + b);
    first + second
}

pub fn bounds_test(
    a: &[i64], a0: i64,
    b: &[i64], b0: i64,
    p: &[i64], q: &[i64],
    level: usize,
) -> Bounds {
    let mut mu_bar = 0i64;
    let mut nu_bar = 0i64;
    for r in 0..p.len() {
        if r + 1 < level {
            mu_bar += mu(a[r] - b[r], 0, p[r], q[r], 0);
            nu_bar += nu(a[r] - b[r], 0, p[r], q[r], 0);
        } else if r + 1 == level {
            mu_bar += mu(a[r], -b[r], p[r], q[r], 1);
            nu_bar += nu(a[r], -b[r], p[r], q[r], 1);
        } else {
            mu_bar += mu(a[r], 0, p[r], q[r], 0) + mu(-b[r], 0, p[r], q[r], 0);
            nu_bar += nu(a[r], 0, p[r], q[r], 0) + nu(-b[r], 0, p[r], q[r], 0);
        }
    }
    // The actual test is: mu_bar <= b0 - a0 <= nu_bar
    // Return as Bounds for the caller to check.
    Bounds { lower: mu_bar, upper: nu_bar }
}
```

### Nonrectangular Extreme

```rust
pub fn extreme_nonrectangular(
    f: &[i64], f0: i64,
    l: &Matrix, ll: &[i64],
    u: &Matrix, uu: &[i64],
) -> Bounds {
    let m = f.len();
    let mut a = vec![0i64; m];
    let mut b = vec![0i64; m];
    a[0] = f0;
    b[0] = f0;
    for j in 0..m { a[j] = f[j]; b[j] = f[j]; }

    // Recursion from n = m down to 1
    for n in (1..=m).rev() {
        let a_n = a[n - 1];
        let b_n = b[n - 1];
        a[0] += pos(a_n) * uu[n - 1] + neg(a_n) * ll[n - 1];
        b[0] += pos(b_n) * ll[n - 1] + neg(b_n) * uu[n - 1];
        for j in 1..n {
            let a_nj = a[n - 1];   // coefficient in position n for bound j
            let b_nj = b[n - 1];
            a[j - 1] += pos(a_nj) * u.get(n - 1, j - 1) + neg(a_nj) * l.get(n - 1, j - 1);
            b[j - 1] += pos(b_nj) * l.get(n - 1, j - 1) + neg(b_nj) * u.get(n - 1, j - 1);
        }
    }
    Bounds { lower: b[0], upper: a[0] }
}
```

## 2.7 `solver/integer.rs` — General integer solver

**Wolfe §4.3, §4.4.** The piece that solves `A·x = b` in integers.

### The formulas

**Gaussian elimination (for real solutions):**
```
procedure GE(A, b) returns (U, c):
    U = A ; c = b
    for k = 1 to m:
        for j = k+1 to n:
            α = -u_jk / u_kk
            U_[j] = U_[j] - α·U_[k]
            c_j = c_j - α·c_k
    return (U, c)
```

**Back substitution:**
```
procedure Back(U, c) returns (x):
    for i = n downto 1:
        x_i = (c_i - Σ_{k=i+1}^{n} u_ik·x_k) / u_ii
    return x
```

**Column echelon form (for integer solutions):**
```
r_j = row of first nonzero in column j, or ∞ if column is zero

Column echelon form:
    r_{j+1} > r_j  if column j is not entirely zero
    column j+1 is entirely zero if column j is
```

**Algorithm ReduceMatrix:**
```
procedure ReduceMat(A) returns (D, U):
    U = I
    D = A
    c = 1
    for i = 1 to m:
        Reduce(i, c:n, D, U)
        if d_ic ≠ 0: c = c + 1
    return (D, U)
end ReduceMat
```

### The algorithm

```rust
pub fn solve_integer_system(a: &Matrix, b: &[i64]) -> IntSolveResult {
    let n = a.cols;
    let m = a.rows;

    // Step 1: Reduce to column echelon form D·U = A, so A·x = b ⟺ D·t = b
    // where x = U·t.
    let (d, u) = reduce_matrix(a);

    // Step 2: Solve D·t = b by back substitution.
    let mut t = vec![0i64; n];
    let mut rank = 0usize;
    for i in 0..m {
        // Find pivot in row i
        let mut pivot = None;
        for j in rank..n {
            if d.get(i, j) != 0 { pivot = Some(j); break; }
        }
        let j = match pivot { Some(j) => j, None => continue };
        // Back-substitute: t[j] = (b[i] - Σ_{k>j} d[i,k]·t[k]) / d[i,j]
        let mut sum = b[i];
        for k in (j + 1)..n {
            sum -= d.get(i, k) * t[k];
        }
        if sum % d.get(i, j) != 0 {
            // No integer solution
            return IntSolveResult::NoSolution;
        }
        t[j] = sum / d.get(i, j);
        rank += 1;
    }

    // Step 3: x = U·t is a particular solution.
    let mut particular = vec![0i64; n];
    for i in 0..n {
        let mut s = 0i64;
        for j in 0..n {
            s += u.get(i, j) * t[j];
        }
        particular[i] = s;
    }

    // Step 4: nullspace basis = columns of U beyond rank.
    let mut nullspace = Vec::new();
    for j in rank..n {
        let mut v = vec![0i64; n];
        for i in 0..n {
            v[i] = u.get(i, j);
        }
        nullspace.push(v);
    }

    IntSolveResult::Solutions { particular, nullspace }
}
```

## The Kahn-style math you need to know

**HNF (Hermite Normal Form):** For integer matrix `A` (n×m, rank n), there exists unimodular `U` (m×m) such that `A·U = H` where `H` is lower trapezoidal, diagonal entries positive, and each diagonal entry is the largest in its row. `H` is unique.

**Algorithm Hermite** (from Wolfe §4.2.3):
```
for i = 1 to n:
    Reduce(i, i+1:n, H, U)    # uses findgcd to reduce h[i, k] to 0 for k > i
    if h_ii < 0: negate h[i], u[i]
    for j = 1 to i-1:
        α = |h_ij / h_ii|
        h[j] -= α·h[i]
```

**What HNF unlocks:**
1. Solving `A·x = b` over integers: `x = U·t`, `H·t = b`, back-substitute
2. Lattice basis: nonzero columns of `H` form a basis of `L(A)`
3. Non-unimodular loop transformations (`T = H·U`)

**Dark shadows** (Wolfe §4.6): for bounds `α·x ≤ c_u` and `c_l ≤ β·x`, the real projection says `α·c_l ≤ β·c_u`, but the dark shadow says `β·c_u - α·c_l ≥ α·β - α - β + 1` guarantees an integer solution.

**Extreme values** (Wolfe §4.7): for `f(x) = F·x + f₀` over `l_{i0} + Σ_{j<i} l_{ij}·x_j ≤ x_i ≤ u_{i0} + Σ_{j<i} u_{ij}·x_j`, the bounding recursion is `b_{n-1,j} = b_{n,j} + b_{nn}⁺·l_{nj} + b_{nn}⁻·u_{nj}` (and analogous for `a`).

# M6–M10 Architecture

## The binding constraint

The checker is currently ~250 lines. It reads `index·i + offset`, compares, exits. Every certificate is one of:

```rust
Claim::Exact(Vec<i64>)   + Witness::IntSolution { i, j }
Claim::None              + Witness::UnsatProof { constraints: Vec<CConstraint> }
Claim::Parametric(...)   + Witness::IntSolution { i, j }
```

Adding any level requires one of:
- **(a)** Fitting its witness into `IntSolution { i, j }` and teaching the checker a *new evaluation function* for the location.
- **(b)** Adding a new `Claim` variant.
- **(c)** Adding a new `Witness` variant.

The architecture question is: **which levels need (a), which need (b), which need (c)?**

---

## The evaluation architecture — the single decisive change

Every level that adds a non-affine index expression needs the checker to *evaluate* that expression. Right now the checker's location computation is hardcoded:

```rust
fn witness_location(access: &Access, iv: &[i64], loop_: &Loop) -> i64 {
    if let Some(ind) = &access.indirect { ... }
    if let Some(range) = &access.range { ... }
    // affine: index·iv + offset
}
```

**The architecture that unifies M6–M10:** replace the hardcoded branches with an `eval_location(access, iv, env)` that dispatches on `access.index_kind`. `index_kind` is an enum. Every non-affine level adds one variant.

```rust
pub enum IndexKind {
    Affine,                          // M0–M5: index·iv + offset
    Product(Box<IndexExpr>),         // M6: i*j, i*i, i*i*j
    Hash(HashExpr),                  // M7: (i*c) >> k, & mask, etc.
    Recurrence(RecurrenceId),        // M8: x[i] via table or closed form
    ModRuntime { base: Box<IndexExpr>, modulus: ParamExpr },  // M9
    FixedPoint { table: Vec<i64> },  // M10: while(x != next[x]) x = next[x]
}
```

`IndexExpr` is a small expression tree that covers M6's products:

```rust
pub enum IndexExpr {
    IV(usize),           // the k-th IV
    Const(i64),
    Add(Box<IndexExpr>, Box<IndexExpr>),
    Mul(Box<IndexExpr>, Box<IndexExpr>),
    // No Div — division collapses to Mod or is rejected
}
```

**The checker's `eval_location` becomes:**

```rust
fn eval_location(access: &Access, iv: &[i64], env: &[(String, i64)]) -> Option<i64> {
    match &access.index_kind {
        IndexKind::Affine => affine_eval(access, iv),
        IndexKind::Product(e) => product_eval(e, iv, access.elem_size),
        IndexKind::Hash(h) => hash_eval(h, iv),
        IndexKind::Recurrence(r) => recurrence_eval(r, iv),
        IndexKind::ModRuntime { base, modulus } => {
            let b = eval_iexpr(base, iv)?;
            let m = modulus.eval(env)?;
            if m <= 0 { return None; }
            Some(b.rem_euclid(m) + access.offset.as_const()?)
        }
        IndexKind::FixedPoint { table } => {
            let mut p = iv[0];
            for _ in 0..table.len() {
                if p < 0 || (p as usize) >= table.len() { return None; }
                if table[p as usize] == p { break; }
                p = table[p as usize];
            }
            Some(p + access.offset.as_const()?)
        }
    }
}
```

**This is the entire architectural move.** Once `eval_location` is a single dispatch, adding a level is: (1) add `IndexKind` variant, (2) add `eval_*` branch, (3) add decision procedure that produces an `IntSolution` witness that `eval_location` will validate.

**The certificate format does not change.** Every level emits `Claim::Exact(Vec<i64>)` with `Witness::IntSolution { i, j }`. The checker verifies by calling `eval_location` on each side and comparing. That's it.

## Per-level architecture

### M6 — Products

**IR:**
```rust
// Access gains:
pub index_kind: IndexKind,  // default: Affine
// IndexExpr as above
```

**Parsing:** the frontend emits `index_kind = Product(parse_iexpr("i*j"))`.

**Decision procedure (`src/decide/m6.rs`):**
```
decide(loop_, p, q):
  1. Both accesses have Product index_kind.
  2. Bound: iv range is [lo, hi). The set of possible products is finite:
     { eval_iexpr(e, iv) : iv ∈ [lo, hi)^depth }
     For depth 1 and |range| ≤ 4096: enumerate. Product set P.
  3. If P_a ∩ P_b = ∅: emit Claim::None with an UnsatProof
     (the disjointness is a finite-set disjointness, expressible as an
     empty intersection of bounded intervals).
  4. If P_a ∩ P_b ≠ ∅: pick the smallest common value v. Find (i, j)
     such that eval_location(a, i) == eval_location(b, j) == v.
     Emit Claim::Exact(vec![j - i]) with IntSolution { i, j }.
  5. If iv range > 4096: refuse. Unknown. (Bounded enumeration cap.)
```

**Checker:** the `product_eval` branch. Evaluates `IndexExpr` over concrete `iv` values with i64 multiplication. Fails on overflow.

**Certificate:** unchanged. `Exact(Vec<i64>)` + `IntSolution { i, j }`.

**Lines:** ~400 in `m6.rs`, ~60 in checker, ~40 in `IndexExpr` parser.

---

### M7 — Hash functions

**IR:**
```rust
pub enum HashExpr {
    MulShiftMask { c: i64, shift: u32, mask: i64 },   // (i*c) >> shift & mask
    XorShift { c: i64, shift: u32 },                   // (i*c) ^ (i >> shift)
    Mul { c: i64 },                                    // i * c (wraps at 64 bits)
}
```

**Decision procedure (`src/decide/m7.rs`):**
```
decide(loop_, p, q):
  1. Both accesses have Hash index_kind with the SAME hash function.
  2. Bound: iv range is [lo, hi). Enumerate hash(i) for i ∈ [lo, hi).
  3. Collision check: which iv values collide?
     - No collision: emit Claim::None with an UnsatProof
       (the hash is injective on this domain).
     - Collision at (i, j): emit Claim::Exact(vec![j - i]) with
       IntSolution { i, j } where hash(i) == hash(j).
  4. If iv range > 65536: refuse. (Bounded enumeration cap for hash.)
```

**Checker:** the `hash_eval` branch. Implements wrapping-multiply, logical shift, bitwise AND/XOR on `u64`. Casts back to `i64`.

**Certificate:** unchanged. `Exact` + `IntSolution`.

**Note:** M7 works only when both accesses share the same hash function. Different hashes → Unknown (equivalent to a mixed-level problem).

**Lines:** ~450 in `m7.rs`, ~80 in checker, ~50 in `HashExpr` parser.

### M8 — Recurrence

**IR:**
```rust
pub struct RecurrenceId {
    pub initial: Vec<i64>,        // x[0], x[1], ...
    pub coeffs: Vec<i64>,         // x[k] = Σ coeffs[j] * x[k-1-j]
    pub domain: (usize, usize),   // iv range over which the subscript is used
    pub table: Option<Vec<i64>>,  // precomputed if domain ≤ 4096
}
```

**Decision procedure (`src/decide/m8.rs`):**
```
decide(loop_, p, q):
  1. Both accesses share the same RecurrenceId OR one is affine (mixed).
  2. If same recurrence:
     a. Precompute table x[domain_lo..domain_hi] by replaying the recurrence.
     b. Enumerate the multiset {x[k] : k ∈ domain}. 
     c. If both accesses cover the same recurrence and same domain:
        the pair is exact iff some k has x[k] appearing at both sides.
        Emit Exact(vec![0]) with IntSolution { i: [k], j: [k] }.
  3. Mixed (one recurrence, one affine A[c*i+d]):
     a. Precompute the recurrence table.
     b. For each c*i+d in the affine range, check if any x[k] equals it.
     c. If intersection is empty: Claim::None.
     d. If intersection nonempty at value v: find k such that x[k] = v
        and the affine i such that c*i+d = v. Emit Exact([i - k]).
  4. If |domain| > 4096: refuse. Unknown.
```

**Checker:** the `recurrence_eval` branch. Replays the recurrence to compute `x[iv[0]]` from `initial` and `coeffs`, verifies the result is `x[iv[0]]`. The recurrence replay is O(iv[0]) per evaluation — bounded by the certificate's `i` and `j`, which are both ≤ 4096.

**Certificate:** unchanged.

**Note:** The `RecurrenceId` lives on `Access`, not on `Loop`. Each access that uses a recurrence index carries its own ID. This means the same loop can have one access using recurrence `A` and another using recurrence `B`, and M8 handles them by finding which indices collide.

**Lines:** ~500 in `m8.rs`, ~60 in checker (recurrence replay), ~30 in `RecurrenceId` struct.

### M9 — Mod-p with runtime modulus

**IR:**
```rust
// Extend M2b's existing RangeExpr::Mod:
pub enum RangeExpr {
    Mod { iv: usize, modulus: i64 },           // M2b (constant modulus)
    ModParam { iv: usize, modulus: ParamExpr }, // M9 (runtime modulus)
    Min { iv: usize, cap: i64 },
    Max { iv: usize, floor: i64 },
}
```

**Decision procedure (`src/decide/m9.rs`):** folds into `m2b.rs`.

```
decide_mod_param(loop_, p, q, env):
  1. Both accesses use RangeExpr::ModParam.
  2. Substitute env into modulus → get concrete p.
  3. If p ≤ 0: Unknown.
  4. If p == p' (both accesses use the same modulus): compute both ranges
     [0, p-1]. Ranges always overlap for p > 0. Emit Exact([0]) with
     IntSolution { i: [0], j: [0] } (both at location 0).
  5. If p ≠ p': compute intervals [0, p_a-1] and [0, p_b-1]. Overlap always
     (both contain 0). Emit Exact([0]) with IntSolution { i: [0], j: [0] }.
  6. If offset differs: subtract; range becomes [offset_a, p_a-1+offset_a]
     vs [offset_b, p_b-1+offset_b]. Standard M2b interval logic.
```

**Checker:** `ModParam` branch in `witness_location`. Substitutes `env` (which the certificate carries as a `Parametric` map), computes `iv[iv_idx].rem_euclid(p)`. Rejects if `p ≤ 0`.

**Certificate:** if the modulus is runtime, the certificate must carry the value of `p`. Two options:

- **(a)** Emit as `Claim::Parametric(vec![("p".into(), vec![ParamExpr::Const(p)])])` with an `IntSolution { i, j }`. The checker extracts `p` from the parametric map.
- **(b)** Emit `Claim::Exact` with `IntSolution { i, j }` and put `p` in a new `Witness::WithEnv` field.

**Pick (a).** The `Claim::Parametric` variant already exists. It serializes the environment. The checker already extracts it.

**Lines:** ~120 in `m2b.rs` extension, ~30 in checker.

### M10 — Fixed-point iteration

**IR:**
```rust
pub struct FixedPointId {
    pub table: Vec<i64>,           // the `next` array
    pub start_expr: IndexExpr,     // how to compute the starting value from iv
}
```

**Decision procedure (`src/decide/m10.rs`):**
```
decide(loop_, p, q):
  1. Both accesses share the same FixedPointId OR one is affine (mixed).
  2. Precompute the functional graph: for each x ∈ table, follow next
     until fixed point or cycle. Memoize.
  3. Same FixedPointId:
     a. The fixed point is a single value f (assuming the graph has one
        sink; if multiple sinks, all paths must terminate at a known set).
     b. If both accesses use the same start_expr: same value → Exact([0]).
     c. If different start_expr: compute both fixed points. If equal →
        Exact([0]). If different → None (UnsatProof by disjointness).
  4. Mixed (one fixed point, one affine):
     a. Compute fixed-point value f.
     b. Check if f is in the affine range [min, max].
     c. If f outside → Claim::None.
     d. If f inside → find affine iv such that c*i+d = f. Emit Exact([i-?]).
        The witness uses i = the starting value (iv for the fixed-point access)
        and j = the affine index.
  5. If table.len() > 65536: Unknown.
```

**Checker:** `FixedPoint` branch. Follows `next` from `iv[0]` until `next[x] == x` or a cycle is detected. Bounded by `table.len()` steps.

**Certificate:** unchanged. The `IntSolution { i, j }` carries the starting IV values. The checker replays.

**Lines:** ~400 in `m10.rs`, ~50 in checker.

## The unified dispatcher

```rust
pub fn decide(loop_: &Loop, p: usize, q: usize) -> (Decision, Option<Certificate>) {
    let ap = &loop_.body[p];
    let aq = &loop_.body[q];

    // Stage 1: same base, not both reads (unchanged)
    if ap.base != aq.base { return (Decision::None, None); }
    if ap.kind == AccessKind::Read && aq.kind == AccessKind::Read {
        return (Decision::None, None);
    }

    // Route on index_kind, most specific first
    match (&ap.index_kind, &aq.index_kind) {
        (IndexKind::FixedPoint {..}, _) | (_, IndexKind::FixedPoint {..}) =>
            return m10::decide(loop_, p, q),
        (IndexKind::Product(_), _) | (_, IndexKind::Product(_)) =>
            return m6::decide(loop_, p, q),
        (IndexKind::Hash(_), _) | (_, IndexKind::Hash(_)) =>
            return m7::decide(loop_, p, q),
        (IndexKind::Recurrence(_), _) | (_, IndexKind::Recurrence(_)) =>
            return m8::decide(loop_, p, q),
        _ => {}  // fall through to M0–M5
    }

    // Existing M2g/M2a/M4/M2b/M3/M5 routes
    if loop_.body.iter().any(|a| a.expr.is_some()) { return m2g::decide(loop_, p, q); }
    if loop_.body.iter().any(|a| a.indirect.is_some()) { return m2a::decide(loop_, p, q); }
    if loop_.body[p].guard.is_some() || loop_.body[q].guard.is_some() { return m4::decide(loop_, p, q); }
    if loop_.body[p].range.is_some() || loop_.body[q].range.is_some() { return m2b::decide(loop_, p, q); }
    if loop_.recursion.is_some() { return m3::decide(loop_, p, q); }
    if loop_.chase.is_some() { return m5::decide(loop_, p, q); }

    // M0
    let (d, c) = m0::decide(loop_, p, q);
    if !matches!(d, Decision::Unknown(_)) { return (d, c); }

    (Decision::Unknown("all levels exhausted".into()), None)
}
```

The ordering matters: **M10 fires before M6 fires before M7 fires before M8.** Fixed-point access is the most restrictive — it must run first. Product next because if an access is `A[(p = next[p]) * 2]`, the fixed-point resolution happens *before* the product is evaluated. Same logic for the rest.

## The honest architectural tradeoff

**You cannot build M6–M10 without the `eval_location` refactor.** The current checker's hardcoded branches don't generalize. But once you pay that cost, each level is a clean addition — the certificate format doesn't change, the checker stays a single verification function, and the soundness argument is one path: *checker evaluates location via `eval_location`, compares, accepts or rejects*.

**The refactor cost is ~270 lines** (IR + checker dispatch). The level costs are ~2,100 lines of decision procedures. The test cost is ~1,000 lines of JSON + shell.

**The risk:** M6's enumerated product set is exponential in loop depth. A depth-3 loop with range 100 has 10⁶ triples. That's not tractable. The refactor needs to *cap* enumeration at depth 2 or total product count ≤ 4096 — otherwise M6 becomes a DoS vector on the analyzer.

**The other risk:** M7/M8/M10 all rely on bounded enumeration. If a level's enumeration cap (4096 for products, 65536 for hashes, 65536 for fixed-point tables) is exceeded, it returns Unknown. That's the honest conservative bound. No level is allowed to use SMT or symbolic solving for the dependence direction — only for the initial enumeration.

> **"The architecture for M6–M10 is: replace the checker's hardcoded location evaluation with `eval_location(access, iv, env)` dispatching on `IndexKind`; add one `IndexKind` variant per level (Product, Hash, Recurrence, ModParam, FixedPoint); each level's `decide` enumerates a bounded candidate set and emits `Claim::Exact` or `Claim::None` with an `IntSolution` witness the checker validates by re-running `eval_location`. The only new dependency: nothing — no SMT, no PIP, no abstract interpretation framework. The bounded-enumeration cap (4k–64k depending on level) is what keeps it sound; exceeding the cap means Unknown, not a wrong answer."**



. Mutual recursion. f calls g calls f. M3 only handles self-recursion. Real code has this (parsers, state machines). Not research, but a level of its own — call it M3.5.
2. Pointer chase through non-literal tables. M5 requires next to be a literal array. Real code loads next from a parameter or another array. Extending M5 to symbolic next requires symbolic execution of the chase — you don't know the visited set without running the code. Bounded symbolic execution is possible but expensive. This is a research problem.
3. Interprocedural dependence. All levels reason within one loop. If A[i] = f(A[i+1]) and f writes to A, the loop body is opaque. Handling this requires a call graph and interprocedural summaries — a whole subsystem, not a level.
4. Aliasing in non-array memory. All levels reason about A[expr] where A is a named array. In JavaScript, obj.field and arr[Symbol()] and Map.get(k) don't fit the array model. Handling these requires a points-to analysis — a pre-pass, not a dependence level.
5. Dynamic bounds. All levels assume the IV range is statically known or parametric. for (i = f(); i < g(x); i++) where f() and g() are function calls — the range isn't known until runtime. This is runtime dependence analysis, which Banerjee explicitly listed as out of scope.
6. Nonlinear index expressions of degree ≥ 3. M6 handles products (i*j). What about i*i*i? That's cubic. My IndexExpr supports it syntactically, but the enumeration blows up. Cubic (and higher) requires actual polynomial Diophantine solving — undecidable in general, decidable only for bounded cases with even worse complexity.
7. Concurrent / parallel dependence. All levels handle sequential loops. If the loop body contains a yield, await, or concurrent write, dependence analysis needs memory-model reasoning. Different problem entirely.
8. Semantic dependence. All levels reason about syntactic index expressions. If the frontend can't figure out what an expression means — a closure, a getter, a computed property — nothing to analyze. This is the frontend's problem, not UDDP's.
9. Assertions and invariants. If the programmer writes assert(i != j) or the frontend can see a loop-invariant constraint, the analysis could use it. Current levels ignore assertions. Adding them requires a constraint language and an assumption discharger.




# Wolfe Chapter 9 — Loop Restructuring

## Extraction for UDDP + SPP

This is the transformation engine. Chapter 9 gives the exact algorithms and legality conditions for every loop restructuring transformation. Here is the extraction, mapped to SPP Layer 2.

---

## 9.1 Simple Transformations

### 9.1.1 Statement Reordering

**What it does:** Reorders statements (or loops) at any granularity.

**Legality condition:** Any topological sort of the dependence graph (including both data and control dependences) is a legal ordering.

**Dependence modification:** None — the dependence graph is preserved; only the linear order changes.

**SPP relevance:**
- Used for instruction scheduling (operation granularity)
- Used for locality (moving statements that use the same data closer)
- Used to prepare for loop fusion (moving loops adjacent)

**UDDP requirement:** A dependence graph with both data and control edges. The certificate is the topological sort order, verified against the dependence graph.

---

### 9.1.2 Unswitching

**What it does:** Removes a loop-invariant conditional from a loop. Replaces:

```
loop
  statements
  if test then then-part else else-part
  more statements
endloop
```

with:

```
if test then
  loop
    statements
    then-part
    more statements
  endloop
else
  loop
    statements
    else-part
    more statements
  endloop
endif
```

**Legality condition:** The conditional test must be **completely independent of the loop**.

**Dependence modification:** None — the dependence relations are preserved.

**SPP relevance:** Reduces branch frequency; simplifies loop body. But makes loop structure more complex, which can affect interchange.

**UDDP requirement:** Prove the conditional test is loop-invariant. Certificate: the test expression is a function of only loop-invariant variables.

---

### 9.1.3 Loop Peeling

**What it does:** Removes the first (or last) iteration(s) of the loop into separate code.

**Transformation:**
```
compute tc
for i = 0 to tc-1 do
  body
endfor
```
becomes:
```
compute tc
if tc > 0 then
  i = 0
  body
  for i = 1 to tc-1 do
    body
  endfor
endif
```

**Legality condition:** Always legal; may require a zero-trip test if the trip count may be zero.

**Dependence modification:** None — the iterations are the same, just separated.

**SPP relevance:**
- Adjusts trip count to enable loop fusion
- Removes conditionals that test the index variable
- Handles wrap-around variables
- Executes loop-invariant code only on the first iteration

**UDDP requirement:** Know the trip count. Certificate: the trip count expression, and the zero-trip guard.

---

### 9.1.4 Index Set Splitting

**What it does:** Divides the index set of a loop into two portions, replicating the body.

**Transformation:**
```
compute tc
for i = 0 to tc-1 do
  body
endfor
```
becomes:
```
compute tc
for i = 0 to s-1 do
  body
endfor
for i = s to tc-1 do
  body
endfor
```

**Legality condition:** Always legal; the union of the split index sets must equal the original.

**Dependence modification:** None — the iterations are the same, just partitioned.

**SPP relevance:**
- Removes conditionals that test the index variable (split at the condition boundary)
- Adjusts trip count for fusion

**UDDP requirement:** Know the split point s. Certificate: the two index sets are disjoint and their union is the original.

---

### 9.1.5 Scalar Expansion

**What it does:** Promotes a scalar to an array to break anti-dependences and output dependences.

**Transformation:**
```
for I = 1 to N do
  T = A(I) + B(I)
  C(I) = T + 1/T
endfor
```
becomes:
```
if N >= 1 then
  allocate Tx(1:N)
  for I = 1 to N do
    Tx(I) = A(I) + B(I)
    C(I) = Tx(I) + 1/Tx(I)
  endfor
  T = Tx(N)
endif
```

**Legality condition:**
- The scalar has **no upward-exposed uses** in the loop (all flow dependences are loop-independent).
- If the scalar is assigned conditionally, last-value assignment may not be possible — may not be feasible unless the scalar is dead after the loop.

**Dependence modification:** Breaks loop-carried anti-dependences and output dependences. Flow dependences become loop-independent.

**SPP relevance:**
- Enables loop fission and distribution
- Enables vectorization
- Removes false dependences that prevent parallelism

**UDDP requirement:** Prove no upward-exposed uses. Certificate: the scalar's def-use chain shows all uses are dominated by a definition in the same iteration.

---

## 9.2 Loop Fusion

**What it does:** Combines two adjacent countable loops with compatible limits into one.

**Transformation:**
```
for I = ... do body1 endfor
for I = ... do body2 endfor
```
becomes:
```
for I = ... do body1 body2 endfor
```

**Legality condition:** All dependence relations must be preserved. Before fusion, all dependences must flow from body1 to body2 (unless carried by an outer loop). After fusion, the loop can carry dependences from body2 to body1 — these would be spurious and illegal.

**Test:** A dependence from iteration i of body1 to any iteration j<i of body2 would be violated by fusion.

**Dependence modification:** Cross-loop dependences become loop-carried dependences. The direction vector for the fused loop includes the cross-loop distance.

**SPP relevance:**
- Reduces loop overhead
- Improves temporal locality (same data reused)
- Enables more scalar optimizations (CSE, instruction scheduling)

**UDDP requirement:** Cross-loop dependence distance. Certificate: the cross-loop distance is positive (or zero for loop-independent).

### 9.2.1 Array Assignments

Fortran 90 array assignments are defined as: compute RHS for all indices, then assign LHS. Simple-minded compilation generates computation loop + copy loop. Fusion eliminates the temporary and copy loop.

**Legality:** Fusion of computation and copy loop is always legal if the LHS array is not used on the RHS.

### 9.2.2 Complications

- **Different trip counts:** Peel or split the longer loop, or use conditionals.
- **Scalars assigned in both loops:** Must ensure correct last value.
- **Upward-exposed use of a scalar in one loop assigned in the other:** Fusion is illegal.

### 9.2.3 Fusing Parallel Loops

- Fusing two vector loops: always legal.
- Fusing two parallel loops: legal if all flow dependences are loop-independent.
- Fusing two doall loops: legal if all resulting dependences are loop-independent.
- Fusing two sequential loops: legal if no dependences are violated.

**Canonical dependence analysis does not compute cross-loop distance.** Wolfe shows how to compute it as the difference between iteration vectors of the two loops.

### 9.2.4 Loop Alignment

**What it does:** Chooses which iteration of the second loop fuses with which iteration of the first.

**Alignment parameter m:** Iteration i of the first loop fuses with iteration i+m of the second.

**Legality:** m is chosen to eliminate negative distance dependences.

**Implementation:** Peeling (peel m iterations) or conditionals (add m iterations, use conditionals to skip).

### 9.2.5 Fusion with Scalars

**Legality rules:**
- Scalar assigned in neither loop or assigned/used in only one loop: does not prevent fusion.
- Scalar with upward-exposed use in either loop that is assigned in the other: **fusion is illegal**.
- Scalar assigned in both loops with no upward-exposed use: fusion is legal if correct last value is assigned.

---

## 9.3 Loop Fission

**What it does:** Breaks a single loop into two or more smaller loops. Inverse of fusion.

**Transformation:**
```
for I = 1 to N do
  A(I) = A(I) + B(I-1)
  B(I) = C(I-1)*X + C
  C(I) = 1/B(I)
  D(I) = sqrt(C(I))
endfor
```
becomes:
```
for ib = 0 to N-1 do
  B(ib+1) = C(ib)*X + C
  C(ib+1) = 1/B(ib+1)
endfor
for ib = 0 to N-1 do
  A(ib+1) = A(ib+1) + B(ib)
endfor
for ib = 0 to N-1 do
  D(ib+1) = sqrt(C(ib+1))
endfor
```

**Legality condition:**
- Construct statement-level dependence graph.
- Find strongly connected components (SCCs).
- Nodes in the same SCC must stay in the same loop.
- If all nodes are in one SCC, fission cannot divide the loop.
- Ignore loop-carried anti-dependences and output dependences for scalars that will be expanded.
- Legal order: acyclic condensation of the dependence graph; any topological order.

**Dependence modification:** Dependences between loops become inter-loop dependences. The SCC structure is preserved.

**SPP relevance:**
- Breaks up large loops for instruction cache
- Improves memory locality (fewer arrays per loop)
- Enables other transformations (interchanging)
- Removes dependence cycles to enable parallelization

**UDDP requirement:** SCC computation. Certificate: the condensation graph and its topological order.

### 9.3.1 Fission with Conditionals

- Treat conditional block as a unit, or
- Use a temporary array to hold the conditional test result, guarding execution after fission.

### 9.3.2 Nested Loops

- Proceed from inner loop outward.
- After processing inner loop, treat each inner loop as an atomic unit for outer loop fission.
- Ignore dependences carried by outer loops when fissioning inner loop.

### 9.3.3 Fission Algorithm

1. Build dependence graph, treating inner loops as atomic units.
2. Ignore dependences carried by outer loops.
3. Ignore loop-carried output and anti-dependences for scalars that can be expanded.
4. Merge nodes for statements that must stay together.
5. Find SCCs.
6. Each SCC becomes a separate loop.
7. Generate code in topological order of the condensation graph.

### 9.3.4 Fission for Parallel Loops

- **Fission for forall loops: always legal** (forall preserves only lexically forward dependences).
- **Fission for doall loops: always legal** (doall carries no dependences).
- **Fission for dopar loops: legal if SCCs respect the parallelism** (dopar resolves all loop-carried conflicts as anti-dependences).

**Use for conversion to array assignments:**
1. If loop has no lexically backward dependences, convert to forall.
2. If there are lexically backward dependences, reorder statements to make them forward.
3. If there are dependence cycles, fission to remove the cycle into a separate loop.

## 9.4 Loop Reversal

**What it does:** Runs a loop backward.

**Legality condition:**
- Reversal of forall, dopar, or dosingle loops: always legal (execution order not defined).
- Reversal of sequential loop: legal only if the loop carries **no dependence relations**.

**Dependence modification:** Negates the dependence distance for that loop in any distance vector.

**SPP relevance:**
- Enables loop fusion where it would otherwise fail (negates cross-loop distance)
- Enables interchanging (negates (<,>) to (<,<))

**UDDP requirement:** Prove no dependence carried by the loop. Certificate: the loop has no loop-carried dependences (all dependences are loop-independent or carried by outer loops).

---

## 9.5 Loop Interchanging

**What it does:** Switches inner and outer loop of a tightly nested pair.

**Legality condition (tightly nested):**
- Loop-independent dependences: cannot prevent interchanging.
- Dependence carried by inner loop before interchange (zero distance in outer): still carried by same loop after interchange — legal.
- Dependence carried by outer loop with zero distance in inner: still carried by same loop — legal.
- **Interchange-sensitive dependence:** Nonzero distance in both loops. Must be carried by the new outer loop in the same way. Only direction vector (<,>) is violated by interchange.

**For two sequential loops:** Interchange is legal if no dependence has direction (<,>).

**Dependence modification:** The distance/direction vector entries for the interchanged loops are switched.

**SPP relevance:**
- **Single most important transformation.** Enables automatic discovery of parallelism.
- Moves dependence-carrying loop to outermost position for parallelization.
- Improves memory locality (changes stride of inner loop).
- Reduces loop startup overhead.

**UDDP requirement:** Dependence direction vectors. Certificate: the direction vector test for interchange legality.

### 9.5.2 Interchanging with Parallel Loops

Same basic rules. But parallel/sequential interchange is more complex:
- A dopar loop resolves all loop-carried conflicts as anti-dependences.
- Sequential loops resolve conflicts in execution order.
- An anti-dependence with positive distance is resolved the same way by both loop types.

### 9.5.3 Multiple Interchanges

- **Outermosting:** Moving a loop to outermost position.
- **Innermosting:** Moving a loop to innermost position.
- Direction vector tests for outermosting/innermosting.

### 9.5.4 Loop Limits

**When inner loop limits are invariant in outer loop:** Interchange without changing limits.

**When inner loop limits vary in outer loop (triangular/trapezoidal):**
- Interchange is equivalent to transposing the iteration space.
- Use Fourier-Motzkin projection to find new limits.
- Algorithm FMint: eliminate variables in order in,in-1,,i2.
- Construct new limits from inequalities involving i1,,ik but not ik+1,,in.

**This is SPP Layer 2's core algorithm for non-rectangular loops.**

### 9.5.5 Nontightly Nested Loops

- Sink nontightly nested code into inner loop by adding conditionals.
- Before-statement: merge with first iteration or prepend new iteration.
- After-statement: merge with last iteration or append new iteration.
- Dependence vectors must add an entry for the sunk code.

### 9.5.6 Interactions with Other Loop Transformations

- **Fission** to make nontightly nested loop tightly nested.
- **Reversal** to enable interchanging (negate (<,>) to (<,<)).
- **Interchanging** to enable fusion.
- **Unswitching** disables interchanging (and vice versa).

---

## 9.6 Loop Skewing

**What it does:** Changes iteration vectors by adding outer loop index to inner loop index.

**Transformation:** Iteration (i,j) becomes (i,j+fi) for skew factor f.

**Dependence modification:** Distance (d1,d2) becomes (d1,d2+fd1).

**Legality condition:** Always legal (unimodular transformation). But the resulting dependence distances must allow the desired subsequent transformation.

**SPP relevance:**
- Enables interchanging when normalization would prevent it
- Enables wavefront execution
- Enables tiling of triangular iteration spaces

**UDDP requirement:** Compute new dependence distances after skewing. Certificate: the transformed distance vectors.

---

## 9.7 Linear Loop Transformations

**What it does:** Unifies interchanging, reversal, and skewing as linear transformations of the iteration space.

**Framework:**
- Transformation matrix T.
- Interchanging: $\mathbf{T}_{\text{int}} = \begin{pmatrix} 0 & 1 \\ 1 & 0 \end{pmatrix}$.
- Reversal: Trev negates the index.
- Skewing: Tskew adds fi to j.
- Composition: matrix multiplication.

**Legality condition:** For sequential loops, 0Td for all dependence distance vectors d.

**Loop limits:** Aic becomes AT-1jc. Apply Fourier-Motzkin projection.

**Unimodular transformations:** (T)=1. Preserve integer points. Volume preserved.

**Nonunimodular transformations:** Allow scaling. Use Hermite Normal Form decomposition T=HU.

**This is the general framework for SPP Layer 2.**

### 9.7.1 Nonunimodular Transformations

- T=HU with U unimodular and H in HNF.
- Transform limits by U first, then H.
- Loop strides are hmm (diagonal of HNF).
- Bounds computation involves floor operations.

**UDDP requirement:** HNF decomposition, Fourier-Motzkin projection, bounds computation for nonunimodular transformations. Certificate: the transformation matrix, HNF decomposition, and transformed bounds.

---

## 9.8 Strip-Mining

**What it does:** Decomposes a single loop into two nested loops: strip loop and element loop.

**Transformation:**
```
for I = 1 to N do body endfor
```
becomes:
```
for Is = 1 to N by s do
  for I = Is to min(N, Is+s-1) do
    body
  endfor
endfor
```

**Legality condition:** Always legal.

**Dependence modification:**
- Distance d becomes (ddivs,dmods).
- If dmods0, another dependence with distance (ddivs+1,-((s-d)mods)) is generated.

**Direction vector modification:**
| Old Direction | New Direction |
|---|---|
| (<) | {(<,<)} |
| (=) | (=,<) |
| (>) | {(>,<)} |

**SPP relevance:**
- Bridge to vectorization (Chapter 12)
- Enables cache blocking
- Enables parallel scheduling
- Enables SIMD

**UDDP requirement:** Strip size s, dependence distances. Certificate: the two new distance vectors.

---

## 9.9 Loop Tiling

**What it does:** Like strip-mining but for nested loops. Tile boundaries are parallel to iteration space axes, not to iteration space boundaries.

**Key difference from strip-mining:** Tile start is independent of first iteration.

**Transformation:** Characterized by tile size ts and tile offset to. Each tile starts at i where $i \bmod ts = to$.

**General formula:**
```
for I = lo to hi do
```
becomes:
```
for It = ... by ts do
  for I = max(lo, It) to min(hi, It+ts-1) do
    body
  endfor
endfor
```

**Legality condition:** Same as strip-mining for the tile loop; interchanging tile and element loops uses the same rules as loop interchanging.

**Dependence modification:** Same as strip-mining.

**SPP relevance:**
- **Core transformation for locality and parallelism.**
- Creates blocks that fit in cache.
- Creates parallel units.
- Creates SIMD units.
- Creates GPU blocks.
- Creates NUMA units.

**UDDP requirement:** Tile size, tile offset, dependence distances. Certificate: the transformed dependence vectors and the interchange legality.

---

## 9.10 Other Loop Transformations

### 9.10.1 Circular Loop Skewing

**What it does:** Skews inner loop iterations to wrap around a cylinder. Iteration space shape preserved.

**Legality condition:** Inner loop must carry no dependences.

**Dependence modification:** Piecewise linear indexing; no change to dependence vectors.

### 9.10.2 Striping

**What it does:** Strip-mining followed by interchange of strip and element loops.

**Transformation:**
```
for I = lo to hi do body endfor
```
becomes:
```
for Is = 0 to s-1 do
  for I = lo+Is to hi by s do
    body
  endfor
endfor
```

**Legality condition:** May not be legal (if negative distance vectors result).

### 9.10.3 Loop Collapsing

**What it does:** Collapses two nested loops into a single loop when array bounds match loop limits and memory stride is constant.

**Legality condition:** Array layout known, strides match.

**SPP relevance:** Fewer loops with longer limits for some machines.

### 9.10.4 Loop Coalescing

**What it does:** Collapses nested loops by computing original index values.

**Transformation:**
```
for I = lo_I to hi_I do
  for J = lo_J to hi_J do
    body
  endfor
endfor
```
becomes:
```
tc_I = hi_I - lo_I + 1
tc_J = hi_J - lo_J + 1
for IJ = 0 to tc_I*tc_J - 1 do
  I = IJ / tc_J + lo_I
  J = MOD(IJ, tc_J) + lo_J
  body
endfor
```

**Legality condition:** Always legal if loop limits are invariant.

**SPP relevance:** Reduces loop nest level; enables parallelization of flattened loop.

---

## 9.11 Interprocedural Transformations

### 9.11.1 Procedure Inlining

**What it does:** Copies procedure body in place of call.

**Legality condition:** Always legal (semantics preserved).

**SPP relevance:** Enables loop transformations across procedure boundaries.

### 9.11.2 Loop Embedding and Extraction

**Loop embedding:** Takes loop surrounding a call and embeds it into the procedure.

**Loop extraction:** Takes loop out of procedure and puts it at call site.

**SPP relevance:** Enables transformations involving loops from call site and procedure.

---

## 9.12 In the Pit

- SISAL has no parallel/sequential interpretation — evaluation order determined by dependences.
- Reduction direction can be defined and used for accumulation operations.
- Loops with only reduction direction dependences can be reversed or interchanged.
- Temporary variables convert control dependence to data dependence.
- Loop reversal with step 1 requires trip count computation:
  ```
  for I = 1 to 10 by 2 do
  ```
  becomes:
  ```
  for I = 1 + ((10-1)/2)*2 downto 1 by -2 do
  ```

3.1 Array Region Analysis (Ch. 8.1)
3.1.1 MayUse, MayMod, Kill Sets
text
MayUse(x) = MayUse(x) ∪ ⋃_{p ∈ PRED(x)} MayUse(p)

MayMod(x) = MayMod(x) ∪ ⋃_{p ∈ PRED(x)} MayMod(p)

Kill(x) = Kill(x) ∪ ⋂_{p ∈ PRED(x)} Kill(p)
UDDP needs this for: Interprocedural subsystem.

3.1.2 Simple Bounds
text
Region = [l₁:u₁, ..., l_d:u_d]

Union:
    [l_d^a:u_d^a] ∪ [l_d^b:u_d^b] = [min(l_d^a, l_d^b) : max(u_d^a, u_d^b)]

Intersection:
    [l_d^a:u_d^a] ∩ [l_d^b:u_d^b] = [max(l_d^a, l_d^b) : min(u_d^a, u_d^b)]
UDDP needs this for: Interprocedural subsystem.

3.1.3 Triplet Notation
text
Union:
    [min(l^a, l^b) : max(u^a, u^b) : gcd(s^a, s^b, l^a - l^b)]

Intersection:
    Solve l^a + i·s^a = l^b + j·s^b
    stride = lcm(s^a, s^b)
UDDP needs this for: Interprocedural subsystem.

3.1.4 Array Kill Analysis
text
Self-conflict: rank of data access matrix = number of loops
               containing assignment ⇒ each iteration assigns different element.

Value-based flow dependence: no intervening killing assignment to same element.
UDDP needs this for: M3, M5 (loop-variant variables).

3.2 Pointer Analysis (Ch. 8.2)
3.2.1 Points-To Relations
text
Triple (p, q, d):
    p = pointer
    q = target
    d = definiteness (D definite, P possible)

Assignment effects:
    1. LHS definite target: kills previous relations for that target.
    2. LHS possible targets: change definite to possible for all targets.
    3. Both RHS and LHS definite: add definite relation.
    4. Otherwise: add possible relations from all LHS targets to all RHS targets.

Merge at CFG merge points: change definite to possible on conflicts.
Loops: iterate until fixpoint.
UDDP needs this for: Points-to/aliasing subsystem.

3.2.2 Array Pointers
text
Fortran 90 array pointers: dope vectors.
Dope vector fields: address, lower/upper bounds, strides for each dimension.
Simple points-to keeps target array name;
more precise keeps dope vector info.
UDDP needs this for: Points-to/aliasing subsystem.

3.2.3 Pointer Arithmetic
text
C arrays defined in terms of address arithmetic.
Extend induction variable analysis to discover starting point,
increment, range of pointer (induction variable of loop).
Can rebuild array references from pointer references for inner loops.
UDDP needs this for: Symbolic pointer chase subsystem.

3.2.4 Allocation Dependence
text
Two dynamic allocation statements: order matters for memory addresses.
Fortran 90: no syntax to get address of pointer target;
            location independence assured.
C: can access/modify addresses; if order important,
   compiler must preserve; insert dependence relations between allocation statements.
UDDP needs this for: Points-to/aliasing subsystem.

3.3 I/O Dependence (Ch. 8.3)
text
I/O dependence: any statement that reads/writes external device
                dependent on any preceding statement that may do likewise.
Preserve order of open, close, rewind, status inquiry, read, write.
Subroutines may contain I/O; assume calls in original order
unless interprocedural info says otherwise.
UDDP needs this for: Effect summaries, interprocedural subsystem.

3.4 Procedure Calls (Ch. 8.4)
3.4.1 Pure Function
text
Pure function: uses but doesn't modify arguments,
               no globals, no I/O;
               return value determined by arguments.

Pure subroutine: only effect is modify read-write/write-only arguments;
                 no I/O or globals;
                 can call only pure procedures.
UDDP needs this for: Effect summaries, interprocedural subsystem.

3.5 Interprocedural Analysis (Ch. 8.5)
3.5.1 Call Graph Construction
text
Triplet ⟨q, k, p⟩: q passed at parameter position k to procedure p.

Cases when processing:
1. Call site doesn't invoke f_k, f_k not argument: skip.
2. Call site doesn't invoke f_k, f_k appears as argument position m:
   add ⟨q, m, a⟩ for actual procedure a, or for a ∈ BoundTo(p, j)
   if invoking formal f_j.
3. Call site invokes f_k:
   add edge p → q;
   add ⟨a, m, q⟩ for actual procedures/formal arguments.
UDDP needs this for: Interprocedural subsystem.

3.5.2 Interprocedural MOD
text
Binding graph: vertices = formal parameters;
edge p_x.f_i → p_y.f_j if p_x calls p_y
passing f_i as reference parameter to f_j.

Find SCCs.
If any argument in SCC locally modified or bound to modified argument,
all in SCC may be modified.
UDDP needs this for: Interprocedural subsystem.

3.5.3 Interprocedural Constant Propagation
text
Jump functions:
    J(q, j) = c        (Const)
    J(q, j) = p.i + c  (Function)
    J(q, j) = ⊥        (NonConst)

Value(f) = abstract value.

Meet operation:
    ⊥ if either ⊥
    ⊤ identity
    ⊥ if different constants
    else constant
UDDP needs this for: Interprocedural subsystem.

## Two honest notes

**1. Ch. 7.6 run-time testing doesn't fit the certificate model.** Every other phase emits a `Certificate` that `m0-check` verifies by replay. Runtime testing emits code that runs *later*, at execution time, on real data. That's not a certificate — it's a **program transformation**. It needs its own output format, its own checker semantics ("if this runtime test passes, independence is guaranteed"), and its own fuzzing infrastructure. I flagged it in Phase 5 but it may deserve its own sub-phase or a full phase.

**2. Interprocedural is where the plan will slip the most.** Phase 8's 5,500-line estimate is optimistic. A real context-sensitive interprocedural analysis with summaries, points-to, and effect composition is what `rustc`'s borrow checker, LLVM's `-steensgaard`, and Soot's whole-program analysis took **years** to get right. The line count is small; the correctness bar is very high. Expect Phase 8 to take 2–3× the estimate.
